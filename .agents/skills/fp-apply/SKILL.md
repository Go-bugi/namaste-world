# fp-apply

## 이 스킬이 존재하는 이유

계산 규칙이 UI, 상태 저장소, 렌더 루프, IO 코드에 흩어지면 테스트할 수 없고, 규칙이 바뀔 때마다 여러 곳을 고쳐야 합니다. 이 스킬은 코드를 하나의 기준으로 나눕니다.

> **사이드 이펙트는 대부분의 함수에서 밀어내고, 규칙은 순수 함수에 모은다.**

함수형 프로그래밍을 한 문장으로 줄이면 "불변 값을 다루는 순수 함수로 프로그래밍하는 것"입니다. 아래 원칙은 모두 이 문장에서 나옵니다. 이 문서는 어떤 언어에도 통하는 원칙만 다루고, 구체적인 문법과 환경 제약은 언어별 문서에 둡니다.

## 핵심 구분: 데이터, 계산, 동작

| 구분 | 무엇인가 | 예 |
| --- | --- | --- |
| 데이터 | 불변 값. 그 자체로는 아무 일도 하지 않음 | 목록, 설정, 이벤트, 상태 스냅샷 |
| 계산 (순수 함수) | 같은 입력이면 항상 같은 출력. 바깥에 영향 없음 | 정렬, 필터, 검증, 상태 전이, 집계 |
| 동작 (사이드 이펙트) | 실행 시점이나 횟수에 따라 결과가 달라지거나 바깥을 바꿈 | 네트워크, 파일, 현재 시각, 랜덤, 화면 그리기, 로그 |

목표는 동작을 없애는 것이 아니라 **동작을 얇게 만들고 계산을 두껍게 만드는 것**입니다. 동작을 포함한 함수를 부르는 함수도 동작이 되므로, 동작은 바깥 가장자리에 모읍니다.

## 경계: functional core와 shell

- **core**: 데이터 정의와 계산(순수 함수)만 있는 층. UI 프레임워크, 상태 저장소, 렌더링 엔진, 플랫폼 API를 import하지 않습니다.
- **shell**: 입력을 받고, core를 호출하고, 결과를 바깥에 반영하는 얇은 층. 이벤트 핸들러, 저장소 action, 렌더 루프, IO 경계, 프로그램 진입점이 여기에 속합니다.
- core는 shell을 모르고, shell만 core를 압니다. 불순한 기능이 core에 필요하면 core가 직접 부르지 않고 **인수로 받습니다**.

어느 코드가 core이고 shell인지는 각 언어별 문서의 "경계" 절에 있습니다.

## 작업 순서

1. **요구사항을 타입으로 옮깁니다.** "A이거나 B"는 합 타입(판별 유니온, enum), 헷갈리는 같은 원시 타입은 newtype, 함께 써야만 의미 있는 값은 하나의 구조로 묶습니다. 잘못된 조합은 아예 만들 수 없게 합니다.
2. **시그니처부터 씁니다.** 큰 함수와 그것이 쓸 작은 함수들의 시그니처를 먼저 정하고, 큰 함수를 구현해 조합이 맞는지 확인한 뒤 작은 함수를 하나씩 채웁니다.
3. **입력과 결과 사이의 관계를 문장으로 나열합니다.** 문장 하나를 식 하나로 옮기면 함수 body가 됩니다.
4. **불순한 입력을 인수로 바꿉니다.** 현재 시각, 랜덤, 설정, 이전 상태는 함수 안에서 읽지 않고 인수로 받습니다.
5. **동작의 위치를 정합니다.** 동작이 일어나는 곳은 "입력 받기 → core 호출 → 결과 반영"만 합니다.
6. **상태의 위치를 정합니다.** 상태 저장소에는 원본 값만 두고, 갱신은 "현재 값 → 새 값" 순수 함수로 합니다.
7. **테스트할 수 있는지 확인합니다.** core 함수는 "인수 → 결과 비교"만으로 검증할 수 있어야 합니다.
8. **make it work → make it right → make it fast** 순서를 지킵니다. 측정하기 전에 캐시나 메모이제이션을 넣지 않습니다.

## 원칙

### 1. 거짓말하지 않는 시그니처

시그니처가 body가 하는 일을 전부 말해야 합니다. 호출자가 구현을 읽어야만 안전하게 쓸 수 있다면 고칩니다. 다음은 모두 시그니처의 거짓말입니다.

- 반환 타입에 없는 실패 (예외, panic, `null`)
- 숨은 입력 (전역 변수, 상태 저장소, 현재 시각, 랜덤)
- 숨은 출력 (인수 변경, 전역 변경, 아무것도 반환하지 않으면서 무언가를 바꿈)

### 2. 순수 함수의 세 규칙

| 규칙 | 어긴 증상 |
| --- | --- |
| 값 하나를 반환한다 | 반환값 없이 무언가를 바꾼다 |
| 인수만으로 계산한다 | 바깥 상태나 현재 시각을 읽는다 |
| 기존 값을 바꾸지 않는다 | 인수로 받은 컬렉션이나 객체를 고친다 |

규칙을 어긴 함수는 세 가지 기법으로 고칩니다.

| 기법 | 쓰는 때 |
| --- | --- |
| 상태를 인수로 넘기기 | 바깥 상태, 필드, 현재 시각을 읽는다 |
| 복사본을 바꿔 새 값으로 반환하기 | 인수를 바꿔야 결과가 나온다 |
| 저장하지 않고 다시 계산하기 | 다른 값에서 계산할 수 있는 값을 따로 저장한다 |

상태 보관(추가, 삭제, 조회)은 컬렉션이나 저장소가 맡고, 규칙은 순수 함수가 맡습니다. 관심사가 나뉘면 상태를 숨기려고 만든 래퍼 메서드가 필요 없어집니다.

### 3. 불변 값과 "관계 → 식"

인수를 바꾸는 함수는 호출자와 상태를 공유하게 됩니다. 변경은 항상 새 값을 만드는 것으로 표현합니다. 이전 값이 그대로 남으므로 비교, 되돌리기, 동시 접근이 쉬워집니다.

구현할 때는 먼저 관계를 나열합니다. 예: "끼워 넣은 목록 = 기준 위치 앞부분 + 새 원소 + 기준 위치부터 끝까지". 각 문장을 이름 붙은 식 하나로 옮기면 실행 순서를 신경 쓸 필요가 없는 코드가 됩니다.

### 4. 함수를 값으로: 고차 함수와 커링

- 함수들이 한 조각(정렬 기준, 점수, 조건)만 다르면 그 조각을 **함수 파라미터**로 뽑습니다.
- 파라미터를 늘려도 호출부에 같은 인수가 반복되면 **함수를 반환하는 함수(커링)** 로 바꿉니다. **덜 바뀌는 인수를 앞에** 둡니다(설정 → 정책 → 데이터).
- 부분 적용은 의존성 주입과 같습니다. 앞 인수로 의존성을 한 번 넣고, 뒤 인수로 실제 입력을 받습니다.

어떤 고차 함수를 쓸지는 결과의 모양으로 고릅니다.

| 원하는 결과 | 연산 |
| --- | --- |
| 같은 개수, 다른 값 | map |
| 일부만 | filter |
| 원소마다 0~N개로 펼치기 | flatMap |
| 값 하나로 줄이기 | fold / reduce |
| 모두 / 하나라도 만족 | every(all) / some(any) |
| "여러 개의 실패 가능 값"을 "실패 가능한 여러 값"으로 | sequence / traverse (collect) |

같은 이름의 연산이 컬렉션, 실패 가능 값, 비동기 값, 스트림에서 같은 의미로 반복됩니다. 한 번 익힌 직관을 다른 타입에도 그대로 씁니다.

### 5. 파이프라인과 식

- 중첩 루프와 결과 누적은 "각 X마다 Y들을, 각 Y마다 Z를"이라는 파이프라인입니다. flatMap 체인으로 쓰고, 뒤 단계가 앞의 여러 값을 써야 하면 중첩합니다.
- 문(statement) 대신 식(expression)을 씁니다. 모든 분기가 값을 내게 하면 빠뜨린 분기가 생기지 않습니다.
- 필터링을 일반화하려면 "조건이 맞으면 원소 하나, 아니면 없음"을 돌려주는 함수를 flatMap에 넘깁니다.
- 새 규칙은 파이프라인에 단계 하나를 추가하는 것으로 들어와야 합니다. 기존 분기를 고치고 있다면 구조를 다시 봅니다.

### 6. 에러를 값으로

실패할 수 있는 함수는 예외나 `null` 대신 실패를 나타내는 값을 반환합니다.

| 상황 | 반환 타입의 모양 |
| --- | --- |
| 항상 성공 | `T` |
| 결과가 없을 수 있음 | `Option<T>` |
| 실패 이유가 필요함 | `Result<T, E>` (성공 타입이 먼저) |
| 동작이 있고 실패 가능 | 비동기/IO 안의 `Result` |

- **대안은 값으로 붙입니다(orElse).** try-catch 중첩 대신 "실패하면 이 값/이 계산"을 조합합니다.
- **비싸거나 동작이 있는 대안은 지연 실행합니다.** 대안을 미리 값으로 만들어 넘기면 성공했을 때도 계산되고 실행됩니다. 상수 기본값은 그대로 넘기고, 계산이나 IO가 필요한 대안은 "실패했을 때 부를 함수"로 넘깁니다.
- **외부 입력은 경계에서 파싱합니다.** 네트워크 응답, 파일, 사용자 입력, 다른 프로세스에서 온 값은 경계에서 한 번 검증해 도메인 타입이나 실패 이유로 바꿉니다. core 안쪽은 검증된 타입만 다룹니다.
- **여러 개를 처리할 때는 전략을 고르고 시그니처로 드러냅니다.**
  - best-effort: 성공한 것만 모읍니다. 일부 결과라도 쓸모 있을 때. 버린 항목과 이유도 함께 돌려주는 편이 좋습니다.
  - all-or-nothing: 하나라도 실패하면 전체 실패. 부분 결과가 오해를 부를 때.
  - 결과 개수를 입력과 비교해야만 실패를 알 수 있다면 전략을 잘못 고른 것입니다.
- 예외와 panic은 불가능한 상태(프로그래밍 오류)에만 씁니다.
- 반환 타입을 먼저 바꾸고 컴파일 에러를 따라가며 고칩니다. 다만 타입이 맞아도 로직이 맞는지는 테스트로 확인합니다.

### 7. 요구사항을 타입으로

잘못된 조합의 데이터를 아예 만들 수 없게 모델링하면 런타임 검증과 테스트가 줄어듭니다.

| 문제 | 해결 |
| --- | --- |
| 같은 타입 파라미터의 순서를 헷갈림 | newtype |
| 플래그일 때만 의미 있는 필드가 있음 | 합 타입 (판별 유니온, enum) |
| 값이 정해진 몇 가지뿐인데 문자열로 받음 | 닫힌 합 타입 |
| "비어 있으면 조건 없음" 같은 암묵 규약 | 조건을 데이터(합 타입의 목록)로 표현 |
| 함께 써야만 의미 있는 파라미터가 흩어져 있음 | 하나의 곱 타입(구조체)으로 묶음 |

- **곱 타입(AND) + 합 타입(OR) = 대수적 데이터 타입(ADT).** 동작은 패턴 매칭으로 경우마다 처리하고, 컴파일러가 처리 누락을 잡게 합니다. 와일드카드로 누락을 숨기지 않습니다.
- **데이터와 동작을 분리합니다.** 합 타입은 동작을 담지 않고 경우가 닫혀 있습니다. 상속과 달리 새 경우를 추가하면 처리하는 모든 곳이 컴파일 에러로 드러납니다. 모델 변경 → 컴파일 에러 목록 = 수정할 곳의 목록.
- **동작도 데이터로 모델링합니다.** 검색 조건, 명령, 필터처럼 파라미터 조합에 숨은 규칙이 있으면 각 경우를 합 타입으로 만들고 목록으로 받습니다. 조건이 없으면 "모두 만족"이 참이 되므로 "빈 목록 = 전체"가 규약이 아니라 결과로 나옵니다.
- 가능하면 런타임 검증보다 컴파일 타임 보장을 택합니다.

### 8. 사이드 이펙트는 바깥으로

- **동작의 실행과 동작 결과의 사용을 나눕니다.** 데이터를 가져오는 코드와 가져온 데이터로 계산하는 코드를 다른 함수로 둡니다.
- **동작은 실행 전의 값으로 다룹니다.** "나중에 실행할 동작"을 값(함수, thunk)으로 들고 다니면 재시도, 대안, 시간 제한을 값의 조합으로 만들 수 있습니다. 실행은 가장 바깥 한 곳에서 합니다.
- **동작이 퍼지는 것을 숨기지 않습니다.** 동작을 쓰는 함수는 시그니처(비동기 타입, 결과 타입)에 그 사실이 드러나야 합니다.
- **불순 함수는 인수로 주입합니다.** core는 필요한 외부 기능의 시그니처 묶음만 알고, 실제 구현은 바깥에서 넘깁니다. 테스트에서는 고정 값을 돌려주는 구현을 넘깁니다.
- **본업이 아닌 일은 파라미터로 밖에 맡깁니다.** 재시도, 캐시, 타임아웃, 연결 관리가 그렇습니다. 좋은 설계에서는 최적화가 "의존성 하나 교체"로 끝납니다. 최적화하려고 계산 로직을 고쳐야 한다면 관심사가 덜 나뉘었다는 뜻입니다.
- **본질적인 규칙은 최대한 순수 함수 안에 둡니다.** 재시도 정책이나 기본값이 결과의 의미를 바꾼다면 그것도 본질적인 규칙일 수 있습니다. 어느 쪽이든 시그니처에 드러나게 합니다.
- 데이터 접근 계층은 시그니처 묶음으로 먼저 정의하고, 계산 로직을 다 쓴 뒤 구현을 붙입니다.

### 9. 상태

- 상태 저장소에는 **원본 값만** 둡니다. 계산할 수 있는 값은 계산합니다.
- 갱신은 **"현재 값 → 새 값" 순수 함수를 넘기는 원자적 갱신**으로 합니다. 읽기, 계산, 쓰기를 나눠서 하면 그 사이에 다른 갱신이 끼어듭니다.
- 저장소의 갱신 함수 안에 조건 분기가 쌓이기 시작하면 core 함수로 옮길 때입니다.
- 매 프레임처럼 아주 자주 바뀌는 값은 예외적으로 가변 참조로 다룰 수 있습니다. 이때도 "얼마나 바꿀지"는 순수 함수로 계산합니다.

### 10. 비동기, 동시성, 흐름, 자원

- **가능하면 순차로, 필요할 때만 동시로.** 서로 의존하지 않는 작업만 동시에 실행합니다. 동시에 실행할 작업을 값의 목록으로 만들고 한 번에 실행하는 것이 가장 단순합니다.
- **공유 상태는 원자적 갱신 함수로만 바꿉니다.** 잠금을 잡은 동안에는 순수 계산만 하고 IO는 잠금 밖에서 합니다.
- **백그라운드 작업은 핸들을 값으로 돌려줍니다.** 시작하는 함수가 작업을 기다리거나 중지할 수 있는 값을 반환합니다. 진행 중인 결과가 필요하면 그 결과를 읽는 수단(채널, 구독)도 함께 돌려줍니다.
- **개수를 모르는 흐름은 생산자와 소비자로 나눕니다.** 생산자는 언제 가져올지와 실패하면 다시 시도할지를 맡습니다. 소비자는 받은 값으로 무엇을 판단할지만 맡습니다. 판단은 목록을 받는 순수 함수로 만들면 흐름과 상관없이 테스트할 수 있습니다. 시간 간격(속도 제한, 주기)도 별도의 층으로 둡니다.
- **재귀와 반복에는 종료 조건이 있어야 합니다.** "될 때까지 다시 시도"의 횟수나 시간 제한은 바깥에서 붙입니다.
- **획득한 자원은 획득한 곳에서 해제합니다.** 획득, 사용, 해제를 하나의 값이나 범위로 묶어 실패해도 해제되게 합니다.

### 11. 테스트

- 테스트는 **함수를 호출하고 결과를 비교하는 것**입니다. 셋업, 호출 순서 검증, 시간 조작이 필요하다면 함수에 아직 불순한 부분이 남아 있습니다.
- 우선순위: 동작 없는 core 함수 → 의존성을 고정 값으로 넘긴 조립 함수 → 실제 경계를 쓰는 통합 테스트(통합이 본업인 코드만).
- 기대값은 구현이 아니라 **요구사항으로 직접 계산**해 주석에 남깁니다.
- **속성 기반 테스트**는 요구사항에서 속성을 뽑습니다. 예: "결과는 항상 0 이상 100 이하", "같은 입력을 두 번 넣어도 결과가 같다", "입력이 늘면 결과가 줄지 않는다". 실패하면 먼저 "테스트가 틀렸나, 버그인가"를 따지고, 생성되는 입력 범위가 요구사항과 맞는지 확인합니다. 큰 수의 합에서 생기는 오버플로처럼 사람이 떠올리지 못하는 경우를 잘 찾아냅니다.
- mock 라이브러리 대신 의존성에 고정 값을 넘깁니다. stub은 함수에 넘기는 값일 뿐입니다.
- 새 기능은 실패하는 테스트 → 가장 단순한 구현 → 작은 함수로 추출(red → green → refactor) 순서로 만들 수 있습니다.

## 리뷰 체크리스트

위에서부터 확인하고, 걸리는 항목은 근거(파일:줄)와 함께 짚습니다. 언어별 문서의 체크리스트도 함께 봅니다.

1. **시그니처가 거짓말하지 않는가?** 반환 타입에 없는 실패, 숨은 입력, 숨은 출력.
2. **계산 규칙이 core에 있는가?** UI, 저장소 갱신, 렌더 루프, IO 경계 안의 조건 분기.
3. **core가 shell을 import하지 않는가?**
4. **불가능한 상태를 만들 수 있는가?** 플래그 조합, 같은 원시 타입 여러 개, "빈 값이면 특별한 의미" 같은 규약.
5. **합 타입 처리에서 누락을 컴파일러가 잡는가?** 와일드카드나 기본 분기로 덮고 있지 않은가.
6. **파생 값을 저장하고 있지 않은가?**
7. **외부 입력이 경계에서 파싱되는가?**
8. **예상 가능한 실패를 예외로 던지고 있지 않은가?**
9. **동시성이 정말 필요한가? 공유 상태 갱신이 원자적인가?**
10. **자원이 실패해도 해제되는가?**
11. **테스트하려면 무엇이 필요한가?**

## 냄새

| 보이면 | 의심할 것 |
| --- | --- |
| 테스트에 셋업이나 mock이 필요하다 | 숨은 상태나 사이드 이펙트 |
| 결과 개수를 입력과 비교해야 실패를 안다 | best-effort를 잘못 고름 |
| 플래그 옆에 "그 플래그일 때만" 쓰는 필드 | 합 타입 누락 |
| 인수 순서를 바꿔도 컴파일된다 | newtype 필요 |
| 계산 함수 안에 연결 생성, 쿼리 문자열, 정리 코드 | core 오염 |
| 최적화하려면 계산 로직을 고쳐야 한다 | 관심사 분리 실패 |
| 인수로 받은 컬렉션을 정렬·추가·삭제 | 호출자의 값을 바꾸고 있음 |
| core에서 현재 시각, 랜덤 | 인수로 받아야 함 |
| 동작을 만들어 두고 나중에 쓰려는데 이미 실행됨 | 실행 전의 값(thunk)으로 다뤄야 함 |
