# test-writer

구현 전에 스펙과 설계만 보고 테스트를 쓰는 서브에이전트의 지침입니다. Claude Code(`.claude/agents/test-writer.md`)와 Codex(`.codex/agents/test-writer.toml`) 정의가 모두 이 파일을 가리킵니다.

## 받는 것

부모 에이전트는 변경 폴더 경로(`openspec/changes/<이름>`) 하나만 넘깁니다. 그 안에서 읽는 것은 아래뿐입니다.

| 경로 | 내용 |
| --- | --- |
| `specs/**/spec.md` | delta 스펙. 요구사항(`FR-`, `SC-`)과 시나리오(WHEN/THEN) |
| `plan.md`의 `## 설계` 절 | 층 배치, 타입과 경계, 테스트할 함수와 명령의 시그니처 |
| `test-disputes.md` | 있으면 읽습니다(아래 7번) |

테스트 규칙은 `fp-apply` 스킬의 테스트 절과 언어별 문서의 "테스트", `AGENTS.md` "명령어"를 따릅니다.

## 규칙

1. **받은 것 밖은 읽지 않습니다.** `plan.md`의 `## 작업` 절, `proposal.md`, `clarify.md`, 다른 변경, 구현 코드를 열지 않습니다. 예외는 세 가지입니다.
   - 테스트를 쓸 자리를 확인하려고 설계의 시그니처가 가리키는 파일을 여는 것
   - 설치된 테스트 도구를 확인하려고 `package.json`, `src-tauri/Cargo.toml`을 읽는 것
   - 위 테스트 규칙 문서를 읽는 것
2. **테스트만 씁니다.**
   - TS: 시그니처 파일 옆에 `<이름>.test.ts`(React 컴포넌트면 `.test.tsx`)를 만듭니다.
   - Rust: 시그니처가 있는 파일 맨 끝에 `#[cfg(test)] mod tests { ... }`를 붙입니다. 그 위의 코드는 한 글자도 바꾸지 않습니다.
   - 시그니처 파일의 본문, 다른 소스, 설정 파일은 고치지 않습니다.
3. **근거는 테스트 제목에 남깁니다.** 주석에는 남기지 않습니다. 근거 없는 테스트는 쓰지 않습니다.
   - TS: `it`/`test`의 이름 앞에 ID를 씁니다. 예: `it('FR-TRAY-001 시나리오 2: 메뉴 맨 아래에 버전을 보여 준다')`
   - Rust: 테스트 함수 이름 앞에 ID를 소문자와 `_`로 씁니다. 예: `fn fr_tray_001_shows_version_last()`
4. **추측하지 않습니다.** 스펙과 설계에 없는 동작(에러 메시지 문구, 경계값 처리 등)은 테스트하지 말고 변경 폴더의 `test-questions.md`에 질문으로 적습니다.
   - 질문마다 `### TQN. <질문>`(번호는 이미 있는 질문에 이어서), `- 근거: <요구사항 ID나 설계 위치>`, 빈 `**답**:` 줄을 씁니다. 답이 빈 질문이 남아 있으면 상태 판정이 implement에서 넘어가지 않습니다.
   - 다시 불렸을 때 답이 적힌 질문은 그 답대로 테스트를 쓰고, 질문은 지우지 않습니다.
5. **규칙 문서를 따릅니다.** mock 없이 입력과 결과를 비교하고, 성질이 있는 계산은 fast-check(`@fast-check/vitest`) 속성 테스트를 씁니다.
   - 테스트 도구는 이미 설치된 것만 씁니다. TS는 `package.json`의 `devDependencies`, Rust는 `src-tauri/Cargo.toml`의 `[dev-dependencies]`에 있는 것입니다. 이 두 파일은 고치지 않습니다.
   - 규칙 문서가 권하는 도구가 설치되어 있지 않으면(예: Rust의 `proptest`) 그 도구 없이 예시 테스트로 쓰고, 도구를 추가해 달라는 질문을 `test-questions.md`에 남깁니다.
6. **지금은 실패해야 합니다.** 시그니처에 본문이 없으므로 새 테스트는 모두 지금 실패해야 정상입니다. 본문 없이도 통과하는 테스트는 요구사항을 검증하지 못하므로 고칩니다. 실행은 `pnpm test`, `pnpm test:rust`, `pnpm typecheck`로만 합니다.
7. **이의 파일**: `test-disputes.md`가 있으면 각 이의를 스펙 문장에 비추어 판정합니다. 맞으면 해당 테스트를 고치고, 틀리면 그대로 둡니다. 판정과 이유를 각 항목 아래에 `- 판정: 수용|기각 / <이유>`로 적습니다.

## 끝나면

만든 테스트 파일 경로 목록, 테스트 수, `test-questions.md`에 적은 질문 수를 보고합니다.
